# 标程、对拍与题解编写指南

本子 Skill 隶属 [`xcpc-problem-creator`](../SKILL.md)，负责确保题目算法正确、时限余量充足、经独立交叉验证与子任务部分分验证无误，并产出高质量题解。

---

## 1. 编写标程 `solutions/std.cpp`

### 1.1 `problem.toml` 声明
全题**有且仅有一个**标程（`main = true`），用于生成缺失的 `.ans`（传统题与无交互器多轮通信题）与校验手工样例：

```toml
[solutions.std]
main = true
```

- 编译约定：固定 `-O2`，默认 C++20（如需指定标准可使用 `.17.cpp` / `.20.cpp` / `.23.cpp` 后缀）。
- **OI 子任务题**：`main = true` 的标程默认必须获得**全部子任务满分（100% 总分）**，否则 `verify` 直接报错。

### 1.2 代码与性能红线
1. **最慢耗时 ≤ 50% 时限**（`verify` 硬门禁）：例如 1s 时限则标程最慢测试点必须 ≤ 500ms，2s 时限则 ≤ 1000ms。解法运行默认串行（`-j 1`），计时接近真实评测机。
   - **多轮通信（`runs = N`）**：时限按各轮累计 CPU 时间计（$\sum_{k=1}^N \text{cpu}_k \le \text{time\_limit}$），标程所有轮次合计须 ≤ 50% 时限；内存限制按单轮独立检查。
   - 若超过 50%，应优化算法常数或 I/O，或与用户确认后再调整题面范围/时限；**严禁私自改松 `[limits]`**。
2. **交互题 Flush 纪律**：
   - 每次发出询问或最终答案后必须立刻 flush（`std::cout << ... << std::endl;` 或 `std::cout << std::flush;`）；
   - 若使用了 `ios::sync_with_stdio(false); cin.tie(nullptr);`，切记 `cin` 不再自动 flush `cout`，任何漏刷缓冲都会直接触发 **`ILE`**；
   - 收到错误标记（如协议约定的 `-1`）或输入 EOF 时应立即 `return 0;` 退出，切勿死循环等待。
3. **代码干净、无 UB**：
   - 避免未初始化变量、有符号整数溢出、越界访问；
   - 多组测试仅清空当前组使用的区间 `[0..n]` / `[1..n]`，禁止每组 `memset` 整个全局上限数组；
   - 优先清晰可读的标准写法，不依赖脆弱的编译期黑科技，方便后续直接作为题解参考实现。

## 2. 独立暴力解 / 参考解与部分分解（交叉验证）

单靠一份 `std.cpp` 极易出现「题意理解偏差」或「公式边界写错但自己验不出」的共因错误。除极简签到题外，必须编写至少一份**独立思路**的参考解：

### 2.1 小数据暴力解（`solutions/brute.cpp`）
用最朴素、不易出错的方法（暴力枚举 / 搜索 / $O(n^2)$ 或 $O(n^3)$ DP / 朴素模拟）直接翻译题意，并在 `problem.toml` 中通过 `tags` 限制仅在小数据上运行：

```toml
[solutions.brute]
expect = "AC"
tags = ["sample", "small"]
```

- 既能对所有 `sample` 与 `small` 测试点自动交叉验证，又不会在 `max` 大测试点上浪费时间或触发 TLE。
- 也可额外在 `small` 之外单独注册一份期待超时的同名/同类暴力解（见 [`wrong-gen/SKILL.md`](../wrong-gen/SKILL.md)），用来验证大测试点确实卡掉了暴力复杂度。

### 2.2 独立满分参考解（可选，`solutions/alt_ac.cpp`）
对于中等及以上难度题目，推荐额外编写一份不同思路或不同数据结构的 AC 解法（`expect = "AC"`），全量跑完所有测试点，用于双保险验证标程正确性与时限余量。

### 2.3 OI 部分分解与预期断言（`score` / `subtasks`）
对于声明了 `[[subtask]]` 的 OI 题，建议为每个关键子任务梯度编写对应的部分分解，用 `score` 与 `subtasks` 精确验证「应过子任务稳定 AC、更高子任务稳定被卡」：

```toml
[solutions.sub1_brute]
score = 30                                          # 精确总分，或区间如 score = [20, 40]
subtasks = { "1" = "AC", "2" = ["WA", "TLE"] }      # 逐子任务预期，复用 ExpectVerdict
```

- 同时声明 `score` 与 `subtasks` 时，两者均须满足；
- 若使用 `quitp` 按比例给分（如查询次数越少得分越高），可用 `score = [min_pts, max_pts]` 校验部分分解落在预期得分区间。

## 3. 使用 `stress_package` 差分对拍

在 `validator.cpp` 过自测、`std.cpp` 与 `brute.cpp`（及交互题的 `interactor.cpp`）写完后，**先对拍再大批量造满数据**。

### 3.1 对拍策略
调用 `stress_package`，传入小规模生成器、参数、待比对解法（如 `["std", "brute"]`）、迭代上限 `max_iter` 与时间预算 `timeout`（**同步支持交互题**）：

1. **均匀随机小数据**：如 `-n 8 -v 10` 跑 500 轮，快速抓逻辑与边界 bug。
2. **极小退化与多测**：如 `-n 1`、`-n 2`、`-t 5 -n 6`（测多测清零与跨组状态污染）。
3. **特殊结构小数据**：若为图/树/字符串题，额外对拍小规模链、菊花、稠密图、全同字符集（如字符集大小 `2`）。
4. **交互题对拍**：重点覆盖隐藏答案在两端（`1` / `n`）、极小查询上限边界以及随机种子驱动的自适应策略分支。

### 3.2 反例闭环处理
当 `stress_package` 捕获分歧时：
1. 工具会自动将反例落盘到 `tests/stress-<n>.in`（**不会**自动修改 `problem.toml`），并返回复现种子、生成命令、截断输入、`std` vs `brute` 输出与 checker 诊断；**交互题额外返回截断双向交互日志（`transcript`：`→` 交互器发出 / `←` 选手发出）与 `interactor` 退出信息**。
2. 人工分析该反例：确认是 `std.cpp` 错误、`brute.cpp` 错误、自定义 `checker.cpp` 误判，还是 `interactor.cpp` 协议/自适应逻辑漏洞（若输入本身非法则说明 `generator` 违反 `validator` 约束）。
3. 修复根因后，**将有代表性的反例登记进 `problem.toml` 的 `[[test]]`**（建议设 `tag = "edge"` 或 `tag = "small"`，OI 题记得标注 `subtask`），使其成为永久回归测试点。
4. 重新运行 `stress_package` 直至在目标迭代数内零反例。

## 4. 撰写题解 `editorial.md`

`editorial.md` 会直接排入 XCPC Workstation 的 A4 题解册，撰写时遵循以下规范：

1. **符号与题面严格一致**：变量名（如 $n, m, a_i$）、下标约定（0-indexed 还是 1-indexed）、边界与模数必须与 `statement.md` 完全一致。
2. **推荐结构**：
   - **题意简述 / 关键观察**：用 2–4 句话点破核心性质或转化；
   - **子任务递进（OI 题适用）**：按子任务梯度由浅入深拆解（暴力做法 → 特殊性质 → 满分算法），每档给出明确复杂度；
   - **算法与正确性证明**：说清状态定义、转移/数据结构维护方式与关键引理，不跳过非显然的推导步骤；
     - 交互题：给出精确询问次数上界证明（及对抗自适应交互器的正确性说明）；
     - 多轮通信题：给出编码/解码方案、信息量/比特预算证明与容错分析；
   - **复杂度分析**：明确给出单组与总时间复杂度、空间复杂度（例如 $O(n \log n)$ 时间、$O(n)$ 空间；多轮通信分别说明各轮复杂度）；
   - **实现细节与易错点**（可选）：提示溢出、多测清空、交互 flush、边界特判等常见坑点。
3. **代码克制**：可附核心逻辑代码片段（与 `std.cpp` 保持一致），避免把整份竞赛头文件/宏模板贴进题解影响排版阅读。
4. **出版自检**：写完后调用 `compile_and_diagnose(target: "problem", id: <slug>, book: "editorial")` 与 `render_page_png`，确认公式无语法错误、代码块与表格不溢出版心。
