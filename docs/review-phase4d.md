# Phase 4D 评审记录（插件系统实测）

> 评审对象：复审之后的 6 个提交（`9ae9a0a`、`b6e5ff5`、`3663e16`、`f916e01`、`11759d4`、`ab2d96e`），以及独立仓库 `xcpc-plugins`（`e5c365b`）。截图在 `docs/review-phase4d/`。
> 环境：`xcpc init --example` 生成的临时工作区；`XCPC_DATA_DIR`、`XDG_*` 全部指向临时目录（全新 `<dataDir>`）；不设置 `XCPC_OFFICIAL_PLUGIN_REPO`，直接使用线上官方仓库；`nsh dev`（debug 构建），窗口 960×980；在 niri 下用 linux-cua 操作。
> 严重度：**阻断**（走不通，或结果错误）/ **别扭**（能走但不顺）/ **打磨**（质感问题）。另外单列一节**安全**。
> 只记录不修。为了测完阻断项后面的流程，测试期间在本地临时加过一行补丁（见阻断 1），测完已用 `jj restore` 还原，仓库里没有任何改动。

## 总评

安装链路、沙箱和开发链路的**骨架都是对的**：
- 全新环境打开「工具」能看到 4 个官方工具，一键安装后原地切入；
- 坏插件（渲染时抛异常、死循环、吃内存）都被关在沙箱里，报错能指到 `ui.js` 的真实行号；
- zip 路径穿越、软链逃逸、SHA-256 不匹配全部被拦下；
- `init --vite → link → vite build --watch` 改一行 TSX 后免重启生效，`storage` 里的状态也保留了下来。

但**用户手里的插件系统现在其实用不了**，原因是两个阻断项：

1. 插件目录的文件监听把「读文件」也当成了「改文件」，热重载陷入死循环。结果是插件工具的输入框打不进字、按钮点击丢失。你打包后实测到的「按钮点不了、输入不更新」就是这个问题。
2. 带界面的插件每交互一次，桌面端要花大约 10 秒重建界面。数论与位运算工作台点一个位格，整个应用就卡 10 秒。

这两项不修，其余体验问题都无从谈起。另外有两个问题会直接卡住第三方开发者：`init --vite` 生成的项目依赖一个在 npm 上不存在的包；官方仓库的 `index.json` 不会随 CI 更新。

## 阻断

### 1. 文件监听自激循环，插件工具全部无法操作（已确认根因）

- **现象**（`02`）：在「复杂度与内存估算」的输入框里输入、退格、清空、粘贴，值都会立刻被还原成默认值；点击带界面插件的按钮没有反应；引擎线程空闲时也持续占用 11–40% 的 CPU。
- **根因**：`apps/desktop/src/plugins.rs:1816` 的 `PluginFileWatcher` 没有按事件类型过滤。在 Linux 上 inotify 会上报 `OPEN` / `ACCESS` / `CLOSE_NOWRITE` 这类读取事件，而 `is_relevant_path` 只判断文件名，于是形成下面的循环：
  1. 读 `manifest.toml` 触发事件；
  2. `notifyPluginsChanged()` 让 `pluginsRevision` 加 1；
  3. `ToolsView` 重新调用 `pluginListTools()`，又读一遍 `manifest.toml`；
  4. 回到第 1 步，无限循环。

  实测 5 秒内 `manifest.toml` 被打开 **953 次**。每转一圈，`HeadlessToolRunner` 的 effect（`HeadlessToolRunner.tsx:247`）就把 `formValues` 重置成默认值一次，`PluginUiRenderer` 也会因为 `revision` 变化把会话销毁后重新挂载。
- **为什么测试没发现**：在完整的 `App.tsx` 加上已安装插件的条件下，无头测试稳定复现：`type("id:tool-field-n","7")` 之后值仍然是 `100000`。但现有的 `tools.test.tsx` 用的是 `testHarness.tsx`，它不会启动 `startPluginWatch()`，所以测不到。
- **验证**：在本地临时加上「忽略 `EventKind::Access(_)`」之后，4 秒内 `open` 次数降到 0，引擎 CPU 降到 0%，输入实时生效（`03`）。
- **建议**：监听只接受 Create、Modify(Data/Name)、Remove 三类事件。再补一个用 `App.tsx` 启动、真实开启监听的回归测试。

### 2. 带界面的插件每次交互要卡约 10 秒

- **现象**（`04`）：在「数论与位运算工作台」点一个位格，桌面端整体冻结约 10 秒后才翻转；切进这个工具本身也要 1 秒以上，加载期间的点击会被丢掉；进程常驻内存从 334MB 涨到 1.49GB。
- **定位**：分线程统计了 CPU。QuickJS 所在的 `xcpc-plugin-ui` 线程每次只用约 10ms；JS 侧的 `nsh-engine` 线程用了 **10.4–12.5 秒**。所以瓶颈在 `PluginUiRenderer.tsx` 把整棵 VNode 树应用到界面的那一步（`applyFrameResult` → `upsertTreeSignals` → `VNodeSlot` 重渲染），而不在沙箱。图论画板的节点少，拖拽和输入都很跟手（`05`），说明开销随节点数量增长得很快。`ab2d96e` 的性能优化没有解决这个问题。
- 这是 debug 构建下的数据，建议在 release 构建下复测一下量级。不过就算快 10 倍，也离「1 帧内响应」的要求很远。

### 3. 第三方开发者照着 `init --vite` 走，第一步就会失败

`xcpc plugin init --vite` 生成的 `package.json` 依赖 `"@xcpc/plugin-sdk": "^0.1.0"`，但这个包在 npm 上查不到（404），所以 `npm install` 直接失败。官方仓库自己是用 `file:../2026-11-19-statement/packages/plugin-sdk` 这种相对路径绕过去的，CI 里也是临时改写成 `file:`。需要先发布 SDK，或者让脚手架生成 git / tarball 形式的依赖。

### 4. 官方仓库的 `index.json` 不会随 CI 更新，插件一升级就会安装失败

应用读取的是 `main` 分支上的 `index.json`（`raw.githubusercontent.com/.../main/index.json`），这个文件是手动生成后提交的。CI（`release.yml`）每次运行会先删掉 `official-latest` 这个 release 再重建，只上传新的 zip，**不会回写 `main` 上的 `index.json`**。只要某个插件改了版本号，旧文件名 `xxx-1.0.0.zip` 就从 release 里消失了，而索引还指向它，结果就是应用里所有安装都 404。另外 `index.json` 里的链接用的是 `releases/latest/download`，CI 用的是 `official-latest` 标签，两边的约定也不一致。

## 安全

| 项 | 结果 |
|---|---|
| zip 路径穿越（`../`、绝对路径、软链条目、非法 id） | 全部拒绝 ✅ |
| 开发链接里的软链指向根目录之外（`check`、`link` 和加载时各验证一次，包括先合法 link 再替换成软链） | 全部拒绝 ✅ |
| 仓库安装时 SHA-256 不匹配 | 拒绝安装 ✅（提示文案问题见别扭 10） |
| `ui.js` 死循环 / 内存炸弹 | 2 秒超时、64MiB 上限都生效 ✅ |

**仍需处理**

1. **信任确认只做在前端，而且是「先启用再禁用」**。只有「设置 → 从文件夹/ZIP 安装」会弹出信任确认，具体做法是：安装完成后插件已经是启用状态，再由 TS 调用 `setPluginEnabled(false)` 关掉（`PluginsPane.tsx:661`）。另外三条安装路径完全不经过确认：仓库安装（`plugins.rs:611`）、`xcpc plugin install`、开发链接。实测用 CLI 装上一个声明了 `example.com` 域名的插件，它直接就是启用状态，界面上也没有任何标记。这违反了 `AGENTS.md`「安全边界在 Core 层强制执行」的要求。建议在 Core 里加一个「待信任」状态：声明了权限的第三方插件安装后默认不可运行，由 GUI 确认后才放行。
2. **一个插件出问题会冻结整个应用**。`plugin_ui_dispatch` / `mount` 在 UI 线程上同步调用 `rx.recv()`（`plugins.rs:2474`、`2504`），所以坏插件每触发一次事件，整个桌面就卡满 2 秒的超时。沙箱保护了数据，但没保护住交互。
3. 仓库地址可以用明文 `http://`。由于下载后会校验 SHA，影响有限，但 `index.json` 本身可以被篡改（包括 SHA 一起改）。建议只允许 https，本地回环地址除外。
4. 文案问题：`xcpc plugin list` 仍然给带 `ui.js` 的插件标 `[unsandboxed-ui]`，JSON 输出里也是 `has_unsandboxed_ui`（`main.rs:3845`），但 4D 之后 `ui.js` 已经运行在沙箱里，这个标记是错的。软链逃逸的报错码是 `ZIP_SLIP`，并且前缀重复了一遍（`ZIP_SLIP: ZIP_SLIP: …`）。

## 别扭

5. **装完第一个工具后，其余推荐卡片随之消失**。空态里列着 4 个官方工具，装完一个就切进工具页，另外 3 个要去侧栏底部的「获取更多工具」里找。
6. **安装没有进度提示**。从 GitHub 下载大约 10 秒，期间只有一个「安装中…」，而且按钮变宽造成布局抖动；同时其余所有「安装」按钮都会变灰。
7. **带界面插件出错后只能看堆栈、无法恢复**（`06`）。按钮回调死循环或内存超限后，整个工具区都被替换成「插件界面加载失败」，但这时并不是加载失败，是某个操作超时了。下面是一整段 JS 堆栈，也没有「重新加载」按钮，只能切到别的工具再切回来。
8. **移除官方仓库后找不回来**（`08`）。移除没有二次确认，移除后也没有「恢复官方仓库」的入口，只能手动输入那串 `raw.githubusercontent.com` 地址。空态提示「请检查仓库源配置」也是技术用语。
9. **拉取失败的仓库会被静默忽略**。订阅一个打不开的仓库后，「仓库源 (2)」照常显示，列表里只是少了它的插件，没有任何提示。
10. **仓库安装失败时，提示是原始错误码**（`07`）：`CHECKSUM_MISMATCH: expected sha256 '000…`，而且被截断了。建议改成「安装包校验失败，可能已被篡改，已取消安装」。
11. **手动记一题的弹窗会在鼠标底下跳动**（`09`）。聚焦题目输入框后展开候选列表，弹窗变高并重新居中，输入框上移约 90px，这时很容易点到遮罩上把弹窗关掉（实测关掉了一次）。
12. **图论画板改边表时会重新布局**。手动拖好的节点位置在追加一条边后就丢了。
13. **CLI 和 GUI 能做的事不对等**。CLI 没有「从仓库安装」的命令，`xcpc plugin repo` 只有 list、add、remove 三个子命令。

## 打磨

14. 卡片和列表里仍然显示 `v1.0.0`，每张卡片都带「官方」角标，跟标题「官方推荐工具」重复。上一轮评审已经提过去掉版本号。
15. 弹窗从「正在获取插件目录…」切换到列表时高度会跳变，「仓库源」按钮的位置也跟着变，第一次点击很容易落空。
16. 同一个插件在不同地方的描述不一致：设置页里数论工具写的是「位运算、进制转换与常用数论工具」，仓库里写的是「64 位进制翻转、数论计算与常用模数速查」（manifest 和 index.json 是分开维护的）。手动添加的仓库，名字会先显示成 URL 本身，下面又重复一遍 URL。
17. 设置页里看不出哪个插件是「覆写了内置版本」、哪个「需要联网」。「恢复内置版本」执行成功后没有任何反馈。`⋯` 菜单里只有一项「重载本地插件」，而热重载已经是自动的了，这一项意义不明确，可以去掉。
18. 训练页同时有右上角「+ 记一题」和卡片里的「+ 手动记一题」两个入口，做的是同一件事。
19. 脚手架的细节：`init` 默认生成的是 `--kind oj`；纯 JS 模板仍然生成 `xcpc-plugin.d.ts`（规格说已由 `@xcpc/plugin-sdk/host` 取代）；模板名称写死成 `My Tool Plugin`，不跟随 id；`check` 对「render 一执行就抛错」的插件也报 ok，说明 dry-run 只检查了导出；`pack` 默认把 zip 输出到插件目录里面，如果这个目录被 link 了，会多触发一次热重载。
