# Phase 3C/3D UX 评审记录（附录）

> 本文是 [specs/authoring-ui-refactor.md](./specs/authoring-ui-refactor.md) 的评审证据附录。重构方向与结论以该规格为准；本文保留问题现场与截图，便于逐条追溯。截图在 `docs/review-phase3-ux/`。
> 环境：`xcpc init --example` 生成的示例工作区（C 隐藏的山峰：交互 + 子任务；D 双轮密信中继：多轮；B 带权阶梯漫步：部分分；比赛 oi-mock），`nsh dev`，窗口约 964×980（逻辑像素）。
> 无编译器场景：另起一个宿主进程，PATH 去掉所有 g++/clang++，缓存和配置目录为空，工作区是全新示例。
> 严重度：**阻断**（走不通）/ **别扭**（能走但不顺）/ **打磨**（质感问题）。

## 总评

功能链路基本是通的：交互日志、多轮、子任务矩阵、UB 体检、外部试跑、整场体检都能跑出结果。但**界面是按实现者的心智写的，不是按用户的**，主要有三类问题：

1. **出错时不告诉人为什么**。没有编译器、自测缺失这些最常见的失败，在体检页和出题页都只显示一句「操作没有完成」，或者一个残缺的检查项标题。用户完全摸不着头脑。
2. **术语直接搬上界面**。UB、阻断、预警、验收过期、验题人目录、% TL、AC / TLE 余量、覆盖度、min/sum、断言、收编进 solutions/、interactor、sol:std、runs……一个普通出题人看不懂这个界面。
3. **入口和状态多头**。同一个动作有 2～3 个入口（UB 体检、试跑外部解法、添加子任务）；同一个状态有 6 种叫法（数据未验 / 数据异常 / 未验证 / 未构建 / 验收失败 / 1 项问题）；在比赛里不能构建题目，点进单题又会丢掉比赛上下文。

## P0：边界情况与出错路径（用户反馈 + 复现）

### 0.1 没有编译器时，整条链路只说「操作没有完成」 · 阻断

- 出题页点「验证」：顶部红字「验证题目数据：操作没有完成」，旁边有个「前往工具链设置」，但**从头到尾没出现「编译器」三个字**。

  ![](review-phase3-ux/19-nocc-verify-generic-error.png)
- 比赛「验题体检」点「验收过期/未验题」或「整场 UB 体检」：同样只有「验题体检：操作没有完成」，**这一页连去工具链的入口都没有**。表格里四道题仍是「未构建」，看不出发生了什么。

  ![](review-phase3-ux/22-nocc-readiness-generic-error.png)
- **根因**：`apps/desktop/src/ui/logic.ts` 的 `errorCopy()` 没有处理 `xcpc-judge` 的错误码（`no_compiler`、`compiler_not_found`、`no_main_solution`、`multiple_main_solutions`、`unknown_checker`、`generator_not_found`、`solution_not_found`、`invalid_limit`、`invalid_config` 等），全部落到 `error.generic`。Core 的 `JudgeError::human_message()` 早已写好中文说明（「未检测到 C++ 编译器（g++ 或 clang++）。请在「设置 → 工具链」指定编译器路径……」），只是界面没用上。
- **建议**：
  - `errorCopy` 补齐 judge 错误码，或者直接透传 Core 的 `human_message`；
  - 没有编译器时，体检页和出题页都给出同一条可操作的提示「没有找到 C++ 编译器」，附「去设置」按钮；
  - **更好的做法是提前告知**：打开出题页或体检页时如果已经探测不到编译器，就把「验证」等按钮置灰并就地说明，而不是等用户点了才失败。

  ![](review-phase3-ux/18-nocc-no-upfront-hint.png)

### 0.2「前往工具链设置」落到了「工作区」页 · 阻断

点了之后打开的是 设置 → **工作区**，用户还得自己找「工具链」。

![](review-phase3-ux/20-nocc-goto-toolchain-lands-workspace.png)

### 0.3 工具链页：安装指引不能直接用 · 别扭

- 反引号原样显示（`` `sudo apt install g++` ``），没有渲染成代码，也不能一键复制；
- 只给了 apt / pacman / dnf，没有覆盖 Nix（本项目自己的开发环境就是 Nix）；
- 「PATH」「XCPC_CXX」「-O2，默认 C++20」属于技术细节，普通用户不需要。

![](review-phase3-ux/21-nocc-toolchain-page.png)

### 0.4 体检页的失败原因被截断成检查项标题 · 阻断

人为删掉 B 的 invalid 自测后点一键验收，风险栏只显示「最近一次构建/验收失败：**Validator 存在与自测**」。这是检查项的标题（措辞本身也不通顺），不是原因。真正的原因在单题出题页的「1 项问题」弹层里写得很清楚：「校验器缺少自测用例（需要至少 1 组有效和 1 组无效用例）· 前往处理」。体检页没有把这段说明带过去。

| 体检页（看不懂） | 单题页（看得懂） |
|---|---|
| ![](review-phase3-ux/11-readiness-failed-reason-cut.png) | ![](review-phase3-ux/13-build-tab-has-real-reason.png) |

**建议**：体检页的每条风险都显示具体原因和「前往处理」，点击直接进单题出题页并打开对应弹层。

### 0.5 点体检页的失败行，落到的是「题面」Tab · 别扭

点 B 行后打开的是单题工作室的**题面**，不是出题页。还要再点一次「出题」，再点「1 项问题」才能看到原因；而且已经离开了比赛，返回时回到的是比赛总览，不是体检页。

![](review-phase3-ux/12-row-click-lands-on-statement.png)

### 0.6 在比赛里不能构建或验证单题 · 别扭

比赛工作室只有「题面 / 验题体检」两个 Tab，选中某道题后只有「题面 / 样例 / 题解」，**没有出题页**。想修一道题，就得离开比赛进入单题工作室。

![](review-phase3-ux/01-contest-studio-no-build-tab.png)

**建议**：比赛里选中题目时同样提供「出题」Tab（复用单题的出题控制台），或者至少让体检行点进去之后保留比赛上下文（返回时回到体检页）。

### 0.7 新工作区的题面预览就挂着「4 个错误」 · 别扭

一打开示例比赛，预览底部就是红色的「4 个错误」，内容都是「包含题目包但尚未通过严格验收，请先完成严格验收」，还附着 `problems/xxx/problem.toml` 路径。题面本身没有任何问题，「没验收」也不该叫「错误」，四条一模一样的文案也没有合并。

![](review-phase3-ux/02-preflight-4-errors.png)

### 0.8「自测 (0)」统计错误 · 阻断（数据错）

hidden-peak 的 `tests/validator/{valid,invalid}/<子任务>/` 下有 4 个自测文件，严格验收也通过了，侧栏却显示「自测 (0)」。**根因**：`crates/xcpc-judge/src/ops.rs` 的 inspect 只列顶层文件，没有递归读取规格允许的按子任务分的子目录。另外，体检页对**还没构建**的题一律显示「缺自测」（自测文件其实都在），容易误导。

## 用户提出的「意义不明」术语：白话对照建议

| 现在 | 问题 | 白话建议 |
|---|---|---|
| 验收过期 / 已过期 | 不知道什么过期了 | 「改动后未重新检查」，或者直接并入「需要重新检查」 |
| 验收过期/未验题 (N) | 按钮文案堆概念 | 「检查全部（N 题）」 |
| UB 体检 / 整场 UB 体检 | UB 是 C++ 术语 | 「内存与越界检查」；放进验证按钮的下拉，不单独占顶栏 |
| 阻断 / 预警 | 「阻断」像系统故障 | 「N 个问题需要处理 / N 条提醒」 |
| 存在待处理项 / 可定稿 | 「存在」读起来生硬 | 「还有 N 个问题 / 可以定稿了」 |
| 导入验题人目录试跑 | 「验题人目录」是什么？需要什么结构？ | 「试跑验题人代码…」，点开先说明「选择一个文件夹，按题号 A.cpp、B.cpp 放代码」 |
| 标程最慢 (% TL) / AC / TLE 余量 | 缩写 | 「最慢用时（占时限）」；AC/TLE 余量这一列在示例里永远是「—」，建议去掉 |
| 覆盖度「2 AC 1 错解 缺自测」 | 一格塞三件事 | 拆开或只保留异常（「缺错解」「缺自测」） |
| 数据 / 累计耗时「26 B —」 | 未构建时无意义 | 未构建时整行置空，只保留一个「未检查」 |
| 捆绑测试（min）/ 按点均分（sum） | min/sum | 「全对才得分 / 按通过比例得分」 |
| 部分分解设置得分断言 | 「断言」 | 「设定这个解法应得多少分」 |
| 收编进 solutions/ | 「收编」+ 目录名 | 「加入解法」 |
| 1.00× std / sol:std / gen:gen_n / 20 runs | 内部 ID 和英文 | 「与标程一样快」/ 解法名 / 「运行 20 次」 |
| 评测器「interactor」/ 交互器「×2」 | 侧栏右侧的暗码 | 交互题的评测器行不显示；轮数写成「两轮」，并放在显眼的配置处 |
| 符合预期（ILE）+ ILE 徽章 | 重复，且 ILE 是缩写 | 「卡住了（未刷新输出或协议死锁）· 符合预期」 |
| 导出 Markdown | 格式名 | 「导出报告」 |
| 可用于比赛 / 未验证 / 1 项问题 / 数据未验 / 数据异常 / 验收失败 / 未构建 | 同一个状态 6 种叫法 | 全应用统一成三档：**未检查 / 有问题 / 已通过** |

## A. 交互题（隐藏的山峰）

![](review-phase3-ux/04-matrix-after-verify.png)

- **预期内的结果用了大红块**（打磨偏别扭）：brute_linear 在子任务 2 预期就是 WA，却用实心红块；deadlock 预期 ILE 却只是加粗黑字；D 题 wa_raw 预期 WA 也是黑字。同样是「符合预期」，红不红取决于预期是怎么声明的。底部「仅看异常 (3)」也把这 3 个预期内的 WA 算成了异常。**建议**：红色只用于「不符合预期」。
- **顶栏太挤，题名被截成「隐…」**（打磨）：未验证 / UB 体检 / 试跑外部解法 / 筛选 / 验证，五个控件挤在一行；UB 体检和试跑外部解法在侧栏底部**又出现一次**。建议顶栏只留状态 + 验证（下拉里放内存检查、外部试跑），侧栏不重复。
- **评测器和交互器两行并列**（别扭）：交互题由交互器判题，「评测器」行右侧写着 `interactor`，点进去说「当前使用内置评测器 interactor……可切换为 checker.cpp」，概念上互相打架。

  ![](review-phase3-ux/07-checker-page-interactive.png)
- **ILE 的耗时显示的是 CPU 1–2 ms**（别扭）：实际等了 2.5 s 墙钟才判定，矩阵里写「1 ms」，会让人误以为程序瞬间退出。ILE 应显示墙钟时间。
- **诊断面板里「交互器信息」和「评测器输出」内容完全一样**（打磨）：交互题只保留一个。

  ![](review-phase3-ux/05-ile-detail.png)
- **交互日志每行一个满底色胶囊**（打磨，呼吸感）：蓝紫条纹相间，视觉很重；→/← 也没说明是谁发给谁。建议去掉行底色，只给箭头和左边线上色，表头写明「交互器 → 解法」；日志框高度固定、内部再滚动，而下方大片空白，改成占满面板更好。

  ![](review-phase3-ux/06-transcript.png)
- 侧栏解法标注口径不一致（打磨）：「预期 AC」「30 分」「60–70 分」「预期 ILE」混用。

## B. 多轮通信（双轮密信中继）

![](review-phase3-ux/25-multirun-matrix.png)

- **轮数设置藏在交互器页右上角的「2 轮通信」下拉里**（别扭），侧栏只有一个暗码「×2」。规格里没有 interactor 也可以多轮，这时这个设置该放在哪里？建议放进顶部题型徽标（「多轮通信 ×2」点击即可改）。

  ![](review-phase3-ux/28-runs-setting-in-interactor.png)
- **多轮日志每行都带「#1 / #2」前缀**（打磨）：建议按轮分组，加小标题「第 1 轮」「第 2 轮」，去掉逐行前缀。

  ![](review-phase3-ux/26-multirun-transcript.png)
- 题目没有子任务时，侧栏仍有「子任务」入口（打磨），空状态里有**两个**「添加子任务」主按钮（右上 + 中间）。

  ![](review-phase3-ux/27-subtask-empty-double-cta.png)
- 底部出现「返回题面 / 加入比赛」，而这道题已经在比赛里了（别扭）。
- 交互器代码编辑器开着字体连字，`!=` 显示成 `≠`、`==` 显示成长等号（打磨），读 C++ 时容易混淆。

![](review-phase3-ux/23-subtask-list.png)

## D. 整场验题体检（oi-mock）

![](review-phase3-ux/08-readiness-initial.png)

- 见 P0 的 0.1、0.4、0.5 和术语表。
- **一键验收进行中**：右侧用等宽字体显示 slug `secret-relay`（技术细节），应显示题号和题名；顶部主按钮变成「取消」，同时下方又出现一条进度条，位置跳动（打磨）。

  ![](review-phase3-ux/09-readiness-batch-running.png)
- **全部通过后**，主按钮保留为一个半透明的禁用色块（打磨）。应改为隐藏，或者变成次要的「重新检查」。

- 「导入验题人目录试跑」点下去会直接弹系统目录选择器，没有说明目录该怎么组织（别扭）。

## D′. 比赛验题体检页：逐块拆解（为什么杂乱）

混合状态：A 改动后未重新检查、B 缺 invalid 自测导致失败、C 跑过内存检查、D 通过；另外导入了 alice、bob 两位验题人的代码。

![](review-phase3-ux/30-readiness-mixed-state.png)

### 1. 头部：两层栏，三套状态说法

- 第一层：返回 + 比赛名 +「题面 | 验题体检」分段 + 面板开关。第二层：橙色徽章「存在待处理项」+「已验收 2 / 4」+「2 项阻断 0 项预警」+ 4 个按钮。内容从约 110pt 以下才开始。
- **同一个结论，三种说法、两种颜色**：徽章是**橙色**「存在待处理项」，计数写「2 项阻断」，下方卡片标题是「风险与预警」，而行左边条和风险图标又都是**红色**。「阻断」和「风险」也不是同一个词。
- 「0 项预警」把零值也显示出来，是噪音。
- **4 个按钮里 3 个是低频动作**（整场 UB、验题人试跑、导出报告），却和主按钮并排，违反 §9.1 第 3 条「低频与危险操作收进 ⋯ 菜单」。按钮文案又长（最长 8 个字加图标），964pt 宽时已经挤到窗口边。
- 右上角的面板开关打开的是比赛「属性」抽屉，直接压在页面上：「整场 UB 体检」按钮被拦腰截断，表格右半部被遮住；抽屉里显示的是「A 题在这场比赛中的设置」，跟体检无关；日期、地点两栏的文字从左边截断（「月 24 日…」「⋮ • 完整可导出数据包」）。

  ![](review-phase3-ux/31-readiness-drawer-overlap.png)

### 2. 表格：七列，大部分为空，同一件事编码三遍

- **列太多且价值不均**：「AC / TLE 余量」在全部 4 行都是「—」；「数据 / 累计耗时」把两个指标塞进一格，只用空格隔开（「1.05 MB 23ms」读起来像一个数）；「覆盖度」一格里同时有「1 AC」「2 错解」和红字「自测失败」三件事，中英混写。
- **同一个问题编码三遍**：行左侧 3px 红边条 + 状态列彩色胶囊 + 下方「风险与预警」的红色图标列表。A 是「已过期」（橙色胶囊），左边条却是红的，颜色互相矛盾。
- **两列彩色胶囊**（验收状态 4 种颜色 + UB 3 种颜色）上下交错，整页像撒了彩纸，视线没有落点。「通过(旧)」用半角括号，颜色是橙色，与「已过期」的橙色含义不同。
- **数字对齐**：耗时列「10ms (1%)」「1ms (0%)」左对齐，数字和单位之间有时有空格（「1.05 MB」）、有时没有（「23ms」），不能纵向比较。
- **行能点，但没有任何可点提示**：没有箭头，也看不出悬停态。点进去落在单题的「题面」，见 0.5。
- **没有逐题动作**：想只重查 B，只能「验收过期/未验题」全部重跑。

### 3.「风险与预警」卡片：重复表格，还说不清

- 每条都是：红色图标 + 题号方块「A」+「题目 A（interval-sum）…」。题号说了两遍，还带上 slug。
- 文案是检查项标题（「Validator 存在与自测」）或内部概念（「题目包已变更，验收已过期」），见 0.4。
- 条目不能点，不能直接去修。

### 4. 验题人卡片：同一批数据画两遍，按钮成排

![](review-phase3-ux/32-readiness-with-testers.png)

- 标题「多验题人横向矩阵」是规格里的说法。

### 5. 卡片与排版：三张卡片三种写法

- 表格卡片没有标题；风险卡片标题 13pt 加粗、内边距 12；验题人卡片标题 14pt 加粗、带分割线，内边距又不同。
- 本页用了 11 / 11.5 / 12 / 12.5 / 13 / 13.5 共 6 种字号，低于 design-system §5「正文 13–14px」；颜色有 22 处写死的 rgba 和十六进制值，没走 Token（徽章底色、红边条、文字颜色）。
- 批量运行时插入进度条（截图 09），把整个表格往下推；出错时插入红字横幅，同样推动布局，违反「零位移」。

**结论**：这一页的问题不在某个控件，而在于它同时承担了「状态汇总」「问题清单」「批量动作」「验题人结果」四件事，每件事又用自己的方式重新表达一遍题目状态。重构方向（取消独立页面，状态回到比赛大纲，动作收进「检查 ▾」，验题人结果拆回各题）见规格 §4。
