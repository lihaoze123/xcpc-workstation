## 总评

6B 的骨架基本立住了，主路径都实测跑通：

- 三种入口都能打开诊断窗口：⌘K、`Ctrl+Shift+D`、`XCPC_O11Y=1`。
- 关闭诊断窗口后会停止轮询；再次打开时，打开之前积累的慢事件也能回溯到。
- 关闭主窗口时诊断窗口一起退出，进程干净结束。
- 深色主题会实时同步到诊断窗口。
- 瀑布图、基线对比和 Perfetto 导出都能用。
- 6A 的 Vim 改动达标：去掉 `vim_bridge.rs` 之后，Insert 和 Visual 下单次 Esc 都能退回 NORMAL；斜杠菜单打开时按 Esc 只关闭菜单。
- 图标换成 `nsh-icon-lucide` 之后，粗细统一，没有发现缺失的图标。

主要问题集中在两处：

1. **主窗口仍然暴露技术细节，而且和诊断窗口重复**：「设置 → 关于」保留了「性能 Trace」，配着「录制并导出 Chrome Trace / Perfetto 时间轴（平时零开销）」这样的说明和整页唯一的主色按钮，状态还会随诊断窗口的开关跳变。这与 6B 规定的「主窗口零技术文案、诊断能力收进独立窗口」直接冲突。
2. **诊断图表会误导读者**：编译、IPC 这类离散事件被连成跨越数分钟的斜线并填充面积；应用空闲时没有出帧的时间段被当成帧间隔，帧率图的纵轴被撑到 1.5s，掉帧数报到 13，60Hz 和 120Hz 阈值线都被压在底部看不见。诊断窗口存在的意义就是可信的数字，这一条比视觉问题更要紧。

规格符合性方面有三处缺口：

- 6A 的原生 `<Editor>` 门控其实没有执行，粗体规避写法原样保留，也没有复测结论；
- `linux_chrome.rs` 留下来了，但没有记录理由；
- `design-system.md` 和 `architecture.md` 都没有提到诊断窗口。

质感方面，主窗口的整体气质没有退步，训练页、设置页的留白和层级依然克制。诊断窗口则明显比主窗口「糙」：英文和中文混排、标签被截断、按钮宽度会跳、`·` 分隔符、常驻的操作提示，加上下半屏大片空白。

## 1. 别扭级问题

### A1 「关于」里的「性能 Trace」与诊断窗口重复，还会暴露技术文案

- 现象：「设置 → 关于」的最后一行是「性能 Trace：录制并导出 Chrome Trace / Perfetto 时间轴（平时零开销）」，配的「开始录制」是这一页唯一的实心主色按钮。打开诊断窗口后，它自动变成「停止并导出」（`14-settings-about-diag-open.png`），关闭后又变回「开始录制」（`15-settings-about-diag-closed.png`）。原因是 `startLiveDiagnostics()` 复用了同一个 `startTraceRecording()`。
- 为什么是问题：
  - 违反 6B 原则 2「主窗口零污染」和 design-system §7 的禁用词规则：`Chrome Trace`、`Perfetto`、「零开销」都是开发者实现细节；
  - 诊断窗口已经有「导出 Perfetto JSON」，同一个能力在两处出现，而且两处共享状态，用户在主窗口看到的按钮状态会因为另一个窗口被改动；
  - 「关于」页的视觉重心被一个开发者功能占走了。
- 改法：从「关于」页删掉「性能 Trace」这一行，导出只放在诊断窗口里。「关于」只保留「复制诊断信息」，必要时在下面加一个低调的次级入口「打开诊断窗口」（或者只靠 ⌘K）。`settings.about.trace*` 这组文案一起删掉。

### A2 诊断图表把离散事件连成线，空闲时段被算成卡顿

- 现象：
  - 「排版与预览管线」「IPC 与交互响应」两张图把几次孤立的编译或 IPC 用直线连起来并填充面积。例如 13:07:40 那次 65ms 的编译和 13:09:30 那次 10ms 的编译之间画了一条斜线，看上去像是两分钟内持续在编译（`13-diag-interpolated.png`）；
  - 「帧率与卡顿」：应用空闲时 NSH 不出帧，相邻两帧的间隔被当成帧间隔，纵轴被撑到 1.5s，红色的掉帧柱最高到 13（`12-diag-reopen-frames.png`）。这时 16.67ms 和 8.33ms 两条阈值线都贴在底部看不见，阈值标签还盖住了最右边的数据；
  - 有数据的事件类图例，最新值仍然显示 `–`。
- 为什么是问题：诊断窗口的价值在于让人相信上面的数字。现在的画法会制造「一直很慢」「频繁卡顿」的假象，6C 拿它当基线依据会被误导。
- 改法：
  - 离散事件用散点或细柱画，不连线、不填充面积，图例显示「最近一次」或「窗口内 P95」；
  - 帧间隔只统计「有输入或动画进行中」的帧，或者把超过一定阈值的间隔视为空闲并截断，不计入掉帧；纵轴上限固定在 50ms 左右，超出的部分在顶端用箭头标记；
  - 阈值标签放到绘图区外侧（右侧轴外），不要盖住数据。

### A3 Rating 曲线丢了段位语义；难度趋势折线噪声太大

- 现象（`08-training-charts.png`、`19-dark-training.png`）：
  - Rating 曲线改用 `TimeSeriesChart` 之后，原来的段位底色和按段位着色的数据点都没了，只剩一条单色线和一条淡淡的 3000 阈值虚线。AtCoder 的 2400、2800 这些关键段位边界看不出来；
  - 「做出的题有多难」用逐周或逐月的 P90、P75 两条锯齿线，十年的数据挤在一起，几乎读不出趋势。图例的顺序是 P90 在前、P75 在后，副标题写的却是「75% / 90% 分位」，两者顺序相反；
  - 悬停提示是 nsh-o11y 默认的黑底胶囊，内容是 `2026-09-27 23:30:00`（精确到秒），和应用里其他 Tooltip（实色表面加 1px 边框）的风格不一样。
- 为什么是问题：规格 §2.2 第 4 项写的是用 `TimeSeriesChart`「获得…段位阈值线与比赛注释」，结果是换了组件、丢了信息。训练看板是做题人每天都会看的页面，这里的信息密度和可读性比诊断窗口重要得多。
- 改法：
  - Rating 曲线：恢复段位色带。如果 `TimeSeriesChart` 不支持色带，就在 thresholds 上叠加分段背景；做不到的话，至少把全部段位边界画成带段位色的阈值线，数据点按段位着色；
  - 难度趋势：默认按月聚合，并加 3 期滑动平均；或者只保留 P75 一条主线，P90 改成淡色带；
  - Tooltip：日期只显示到日期本身，样式对齐 design-system §4 的浮层规范。

### A4 Trace 列表实时插入时行位置下移，容易点错；不同场景也能拿来对比

- 现象：
  - 我想选中「ux.inp.nav.space 63.3ms」，点击时恰好插入了一条新的 `startupSyncIfEnabled`，整列下移，结果选中的是 `savePrefs`；
  - 随后对比视图拿 `savePrefs` 和导航 Trace 比，给出「0 slower · 0 faster · 1 new · 3 gone」这种毫无意义的结果，也没有任何提示（`25-diag-compare-mismatch.png`）；
  - 同名的 `ux.inp.nav.space` 有好几条，从名字看不出是切到了哪个空间。
- 改法：
  - 有新 Trace 时不推挤列表，在列表顶部显示「N 条新记录」，点击后再插入；或者在用户悬停或选中列表时冻结列表；
  - 只允许同名 Trace 之间对比，名字不同时给出提示；
  - INP 类 Trace 名称附带目标，例如 `nav → 训练`。

### A5 诊断窗口的标签页被截断，没有自己的标题栏和关闭按钮，标题不跟随语言

- 现象（`04-diag-metrics.png`）：
  - 中文界面下，顶部的分段控件显示成「实时指标 链路追踪 结构化…」，第三个标签被截断；英文界面下能完整显示；
  - 诊断窗口没有使用应用的 44pt `TitleBar`。在 niri 这类不提供服务端装饰的环境里，窗口内没有关闭按钮，只能靠合成器快捷键关闭；
  - 窗口标题在打开时取一次 `t("o11y.windowTitle")`，之后不再更新。切到英文后，窗口内显示 `XCPC Diagnostics`，系统标题仍然是「XCPC 诊断」（`23-en-diag-overlap.png`）。
- 改法：
  - 标签改成「指标 / 追踪 / 日志」，或者让分段控件按内容自适应宽度；
  - 复用主窗口的 `TitleBar`，左侧是状态点和标题，中间放三个标签，右侧放窗口控制按钮；这样顶部可以少一行，信息层级也和主窗口一致；
  - 用 `useWindowTitle` 让窗口标题跟随语言。

### A6 两个基线按钮功能相同，基线无法命名；按钮文字变化导致工具栏抖动

- 现象：
  - 全局工具栏的「捕获基线」和追踪面板里的「存为基线」做的是同一件事（`handleCaptureBaseline` 和 `handleSaveBaseline` 都调用 `saveTraceAsBaseline`），而且都不让用户命名，名字自动生成为「`ux.inp.nav.space (63.3 ms)`」。规格里写的是「命名基线（如『优化前：15 题切题』）」；
  - 在日志标签页点「捕获基线」时，保存的是不可见的「当前选中」Trace，或者最新的一条，用户不知道存的是哪一条；
  - 点击后按钮文字从「捕获基线」变成「✓ 已存为基线」，宽度变大，右边的「导出 Perfetto JSON」被挤得右移约 16px（`11-diag-baseline-shift.png`），违反「不能有 1px 布局抖动」。
- 改法：
  - 删掉全局工具栏里的「捕获基线」，只保留追踪面板里的「存为基线」；
  - 保存时就地弹出一个输入框，默认填入自动名称并全选，回车确认；
  - 瞬态确认只替换图标、不改文字，或者给按钮设一个固定最小宽度。

## 2. 规格符合性

### S1 6A 编辑器门控没有执行，也没有结论

规格 §2.2 第 3 项写的是「实测 NSH 0.7.1 Linux 是否仍渲染多余应用菜单图标，若已修复则删除」。现在 `linux_chrome.rs`（170 行）仍然在 `lib.rs:71` 调用，提交说明和文档里都没有实测结论。建议补一句结论；如果确认已修复，就删掉。

### S3 设计文档和架构文档没有同步诊断窗口

`design-system.md` 和 `architecture.md` 都没有提到诊断窗口、`nsh-o11y`、`TimeSeriesChart`，也没有写分层采集。按 AGENTS.md「设计决定发生变化时，同步更新对应的 `docs/` 文件」，至少要补这几处：

## 4. 应并入 6C 的清单

**性能数据**（来自诊断窗口，debug 构建，只作量级参考）：

1. **启动同步太慢**：`startupSyncIfEnabled` 两次启动分别是 14.7s 和 14.2s。要确认它完全不阻塞首屏和交互，并考虑把同步结果的回填做成增量的；
2. **启动时重复编译**：同一毫秒内出现两次约 259ms 的 `compile`。可能是首屏触发了两次编译，需要去重；
3. **切到训练页的交互耗时偏高**：INP 分别是 54.9、63.3、47.8ms，其中 `trainingDashboard` IPC 占 28–31ms，而且是同步等待的。可以做成预取或缓存，先渲染上一次的快照；
4. 启动时 `toolchainStatus` 耗时 112ms，可以推迟到第一次进入出题或工具链界面时再查。

**交互与视觉**：

5. 第 1 节的 A2 修好之后，才能把帧间隔作为 6C 的验收指标；
6. A3 是用户每天都会看的训练看板，建议放在 6C 打磨的前面处理；
